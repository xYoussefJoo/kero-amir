Performance & Security Report

Kero Amir portfolio + CMS (kero-amir.runasp.net API · Next.js web, pre-launch)
Prepared 14 November 2026

Scope and method

Reviewed: the source code (apps/web: Next.js 16; apps/api: ASP.NET Core .NET 10, EF Core, SQL Server); the production build of the web app served locally (next start, the web app is not deployed yet); and the live API at https://kero-amir.runasp.net (MonsterASP.NET, IIS).

Measured live: Lighthouse 12 (3 runs each, median) on mobile (simulated slow 4G, 4x CPU) and desktop; response headers and redirects with curl; TLS/ALPN negotiation; API latency (30 requests per endpoint, local and live); passive exposure checks (GET on exact paths only); the sign-in rate limit (12 requests with a non-existent test address); npm audit and dotnet list package --vulnerable --include-transitive.

Not measurable here: the web app's production host, CDN and headers (not deployed); real-user Core Web Vitals (no field data yet); HTTP/2 on the API (this client only offered HTTP/1.1). These are marked CHECK, and Section 4 lists the tool that confirms each one. Section 6 is a modelled calculation, not a load test. No intrusive or active security testing was performed.

Status key: OK observed and sound  ·  CHECK needs a measurement or access not available here  ·  FIX issue visible in the page or code

Summary

The build is in good shape for a pre-launch site: accessibility, SEO and best-practice scores are 100, layout shift is zero, the initial JavaScript is lean (195 KB gzip) because three.js only loads on strong desktops, and the API's auth is properly hardened (rate limit, lockout, 2FA, closed CORS, no leaked secrets). The main performance risk is the desktop 3D logo, which blocks the main thread for about 0.8 s while it builds, plus a 14.8 s cold start on the live API after idle. The main security gap is that neither the API nor the web app sends any security headers (no HSTS, nosniff, framing or referrer policy), the HTTPS redirect is temporary, and the API's OpenAPI map is public in production.

Recommendations

  • Build the 3D pieces without freezing the page. In PuzzleLogo3D.tsx, lower curveSegments to 6 and bevelSegments to 2, and build the geometries a few per frame (or in requestIdleCallback) while the 2D logo is still showing.
  • Preload only one header logo. In Logo.tsx, drop priority from the dark-theme variant (or both: the header logo is not the LCP).
  • Keep the API warm. Point a free uptime monitor (e.g. UptimeRobot, every 5 min) at /api/v1/health/live, or enable an "always on" option if the MonsterASP plan has one.
  • Deploy the web app behind a CDN (Vercel as planned) so static pages are served from the edge with Brotli and HTTP/2/3.

Recommended security headers

Start the CSP as Report-Only: a strict policy can break things the page relies on (inline theme script, WebGL, fonts), so watch the reports, then switch to enforcing. Sources below match what the page actually loads today (all same-origin).

Web, apps/web/next.config.ts (also set poweredByHeader: false):

poweredByHeader: false,
async headers() {
  return [{
    source: "/(.*)",
    headers: [
      { key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains; preload" },
      { key: "X-Content-Type-Options", value: "nosniff" },
      { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
      { key: "X-Frame-Options", value: "DENY" },
      { key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=()" },
      { key: "Content-Security-Policy-Report-Only",
        value: "default-src 'self'; img-src 'self' data: blob:; font-src 'self'; " +
               "script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; " +
               "connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'" },
    ],
  }];
},

API, apps/api/src/KeroAmir.Api/Program.cs (JSON only, so the CSP can be strict):

app.UseHsts();                       // with builder.Services.AddHsts(o => { o.MaxAge = TimeSpan.FromDays(730); o.IncludeSubDomains = true; });
app.UseHttpsRedirection();           // permanent: builder.Services.AddHttpsRedirection(o => o.RedirectStatusCode = 308);
app.Use(async (ctx, next) =>
{
    var h = ctx.Response.Headers;
    h.XContentTypeOptions = "nosniff";
    h.XFrameOptions = "DENY";
    h["Referrer-Policy"] = "no-referrer";
    h.ContentSecurityPolicy = "default-src 'none'; frame-ancestors 'none'";
    await next();
});
if (app.Environment.IsDevelopment())
    app.MapOpenApi("/openapi/{documentName}.json");   // keep the API map out of production

Remove X-Powered-By on IIS: in the published web.config (the deploy script already edits it):

<system.webServer>
  <httpProtocol><customHeaders><remove name="X-Powered-By" /></customHeaders></httpProtocol>
</system.webServer>

Contact form hardening (when it is built, Phase 6)

  • Validate and length-cap every field server-side (FluentValidation is already in place); never render submitted HTML.
  • Cloudflare Turnstile plus a hidden honeypot field; verify the Turnstile token on the API, not in the browser.
  • Its own rate limit (e.g. 5 per 10 min per IP) separate from sign-in; email alerts through a background queue.
  • Keep the Resend/Turnstile keys in server environment variables only.

Preview and launch hygiene

  • Set SITE_URL to the production domain before the first public deploy so canonical and hreflang point at it.
  • Protect Vercel preview deployments (Deployment Protection) and send X-Robots-Tag: noindex on previews; /admin already sends noindex.
  • Enable GitHub Dependabot security updates only (no routine version PRs).

How to read this

On a CDN, request rate is rarely the limit; bandwidth and plan quotas bind first. Here the pages are prerendered and cached, so browsing does not touch the API at all: the API is only called when the cache revalidates (hourly, or when Kero publishes) and by the admin. The real bottlenecks are the dynamic endpoints (sign-in today, the contact form later), which are rate-limited and should be tested separately and gently. Check the MonsterASP plan's CPU/bandwidth limits and the web host's data-transfer quota before a launch or campaign. A load-test script is delivered alongside this report: docs/reports/kero-amir-loadtest.js (k6; static pages ramp to 100 users, public API reads at a fixed 5 req/s; it never calls sign-in, admin or write endpoints). Run it only against a deployment you own, ideally staging, outside peak hours.

Assumptions: 19 requests and 571 KB per first visit (measured in the lab); read times of 8/5/3 s; light/heavy scenarios at 0.6x/1.6x the measured request count; repeat visits are lighter because hashed assets are cached for a year. Limitations: findings come from the publicly served content and the source code at the time of review (web app measured on a local production build, API measured live); no intrusive or active security testing was performed. Sharing a PageSpeed Insights run on the deployed site, the curl -sI header output after the fixes, and a k6 summary would let this report be updated with field data.
